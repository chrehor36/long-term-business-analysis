WHY THIS COMMIT HAS NO PATHSPEC, AND WHY THAT IS SAFE HERE. `git commit -- <pathspec>`
takes the WORKING TREE content of the named paths, not the index, so it CANNOT record a
deletion for a file that is still present on disk - it silently re-adds it. That is what
happened in 43f0276: the `git rm --cached` was staged and the pathspec commit resurrected
all thirteen. So this one commits from the index, after verifying two things the fold's
step 6 exists to protect: `git diff --cached --name-status` listed exactly these thirteen
deletions and nothing else, and every other change in the tree is UNTRACKED (`??`), which
a bare commit never picks up. Recorded because it is a real gap in the fold rule: a
pathspec isolates a commit from other sessions, and it also makes a deletion impossible to
record while the file remains on disk.
